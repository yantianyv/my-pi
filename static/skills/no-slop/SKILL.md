# no-slop：AI 产出冗余审查

AI 生成的内容有几类典型冗余。本清单给出**术语 + 判据 + 修法**，诊断时用术语指称问题，不说「有点啰嗦」这类模糊话。

## 审查流程

1. 确定对象：用户指定的文件/diff/文案；未指定时审查最近一轮 AI 改动（`git diff`）。
2. 逐条过下面四张表。**每条命中必须能答上判据问句**，答不上就不报——误报比漏报更浪费用户时间。
3. 修复用最小改法：删多余的部分，**不顺手重构、不顺手改无关代码**。

## 一、代码本体

| 术语 | 判据问句 | 修法 |
|---|---|---|
| 镀金（gold plating） | 需求/指令里有这条吗？ | 删掉没被要求的功能 |
| 过度防御 | 这个分支在现有调用方契约下能走到吗？ | 删不可能发生的判空/兜底/吞异常 catch |
| 投机泛化 | 第二个调用方存在吗？ | 只用一次的抽象合回调用处 |
| 过度配置化 | 它历史上改过吗？一年内会改吗？ | 配置项收回为常量 |
| 兼容性包袱 | 旧值/旧接口真的还在某处存活吗？ | 删迁移代码与兼容分支（同名同义自然承接，读不到走默认值） |
| 边界通胀 | 调用方契约允许这个值吗？ | 删与不变量矛盾的分支 |
| 占位残留 | 今天谁会调用它？ | 删 TODO 注释、无调用方的 stub、「将来可能用到」的参数 |

## 二、注释与文档

| 术语 | 判据问句 | 修法 |
|---|---|---|
| 复读注释 | 删掉注释，信息有损失吗？ | 删；只留「为什么」与非显而易见的约束 |
| 变更史注释 | 出现了「改为/之前是/本次新增」吗？ | 删（历史归 git 与 commit message） |
| 教科书头注 | 头注里有一句代码本身说不出来的话吗？ | 没有就整段删 |

## 三、提示词与对外文案

| 术语 | 判据问句 | 修法 |
|---|---|---|
| 画蛇添足 | 读者看到这句时，这件事大概率已经发生了吗？ | 删（如 fetch 失败建议 web_search——读者多半刚从搜索结果来） |
| 过时引用 | 提到的工具/命令/参数还存在吗？（grep 验证） | 改成现名 |
| 受众错位 | 这段文字的目标读者需要知道这句吗？ | 实现解释从用户文案删除，挪进对话回复 |
| 自证实现 | 这句影响对方下一步做什么吗？（「返回时会报告…」） | 不影响就删 |
| 平行重复 | 同一事实改规则时要同步改几处？ | 收敛为一处，其余只留指引 |

## 四、散文（文档/公告/发布文本）

清嗓开场（「众所周知」「随着…的发展」）、伪洞察（「大多数人忽略的是…」）、二元对立（「不是 X，而是 Y」）、重要性吹嘘（「标志着关键时刻」「至关重要」）、假深刻结尾（结尾金句/比喻收束）、含糊归因（「专家认为」「研究表明」——点名来源或删）、同义词轮换（同一概念换着词叫——重复用同一个词）。

中文特有：「赋能/抓手/闭环/沉淀」类黑话、「在…的道路上」类空转句式、四字格堆砌。

## 输出格式

按术语分组报告，每条：`文件:行号 + 术语 + 判据答案（一句话）+ 最小修法`。没有问题就直说「未发现命中项」，不硬凑。

## 元规则

- 同一条术语在同一项目被用户认可过 **3 次以上** → 提醒用户考虑升格写进该项目的 AGENTS.md。
- 本清单只管「删多余」，不管风格偏好（命名、缩进、句式长短是偏好，不是 slop）。
